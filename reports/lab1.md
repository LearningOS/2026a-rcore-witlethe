# 功能实现

添加了新的系统调用 `sys_trace` (系统调用 ID 为 410) 用来追踪当前任务系统调用的历史信息，并做对应的修改
前两个功能由于没有虚拟内存子系统所以相当于直接操作物理内存，较为简单
第三个功能需要实现内核函数 `syscall` 调用时的副作用，通过抽象出一个高阶函数 `dispatch_with_record` 后实现，系统调用次数是关于任务控制的可变量，在对应结构中实现后将接口映射到 `TaskManger` 中供 `sys_trace` 和入口的 `syscall` 调用

# 问答题

1. 正确进入 U 态后，程序的特征还应有：使用 S 态特权指令，访问 S 态寄存器后会报错。请同学们可以自行测试这些内容（运行 三个 bad 测例 (ch2b_bad_*.rs) ），描述程序出错行为，同时注意注明你使用的 sbi 及其版本

RustSBI 固件版本: `0.4.1` (来自 README)
```bash
[kernel] PageFault in application, bad addr = 0x0, bad instruction = 0x804003a4, kernel killed it.
[kernel] IllegalInstruction in application, kernel killed it.
[kernel] Panicked at src/syscall/fs.rs:11 called `Result::unwrap()` on an `Err` value: Utf8Error { valid_up_to: 3, error_len: Some(1) }
```
kernel 日志提示：出现 PageFault，错误访问了地址 0x0，导致出错的指令来自 0x804003a4，内核将其杀死
kernel 日志提示：应用中出现了非法指令，此处应指 S-mode 特权指令
kernel 日志提示，程序于 sys_write 处崩溃，直接崩溃来源是解析 utf-8 字符串时出错，可能由传入的地址不正确导致

2. 深入理解 trap.S 中两个函数 __alltraps 和 __restore 的作用，并回答如下问题:
    1. L40：刚进入 __restore 时，sp 代表了什么值。请指出 __restore 的两种使用情景
        在刚进入 __restore 时，sp 应指向内核栈
        __restore 可以
        - 用于从 U-mode 到 S-mode 的 trap 中恢复
        - 首次启动一个用户程序
    2. L43-L48：这几行汇编代码特殊处理了哪些寄存器？这些寄存器的的值对于进入用户态有何意义？请分别解释
        t0, t1, t2 都是中间寄存器
        sp 现在指向了内核用户进程对应的内核栈
        sstatus 中存储处理器的状态信息（中断，模式等），他在这里被写入了 Trap 前的状态
        sepc pc 相关信息，它在这里被写入了 Trap 发生前的 ecall 指令的地址
        sscratch 负责辅助栈的切换，这里将用户栈的指针写入 sscratch
        上述 CSR 对于用户态来说都是 Trap 辅助寄存器
    3. L50-L56：为何跳过了 x2 和 x4？
        x2 就是 sp，他将被单独处理
        x4 就是 tp，它的作用与线程的实现有关，在 trap 过程中不需要它
    4. L60：该指令之后，sp 和 sscratch 中的值分别有什么意义？
        - sp : 用户栈指针
        - sscratch ：用户进程对应的内核栈的指针
    5. __restore：中发生状态切换在哪一条指令？为何该指令执行之后会进入用户态？
        sret
        sret 的语义为根据 sstatus.SPP 决定处理器状态切换的目标状态
        恢复中断并修改 PC
        traphandler 处理时 sstatus.SPP 表明当前处于 S-mode，因此调用 sret 会将其切换到 U-mode
    6. L13：该指令之后，sp 和 sscratch 中的值分别有什么意义？
        - sp ： 内核栈指针
        - sscratch ： 用户栈指针
    7. 从 U 态进入 S 态是哪一条指令发生的？
        ecall
